Project Report

Smart Clinic Appointment & Patient Management System (SCAPMS) — COS202 Programming II

1. Project description

SCAPMS is a desktop application for a university clinic, written in C++17 with the Qt 6 GUI toolkit and built with CMake (MSYS2 UCRT64, g++ 15.2). Clinic staff use it to register patients, schedule appointments, manage a waiting queue, search and sort records, undo administrative mistakes, view reports, and save or load all data from a file. The code is divided into four layers, each in its own namespace: scapms::model (the clinic's data classes), scapms::controller (rules and algorithms), scapms::utils (validation, files, IDs, exceptions) and scapms::gui (Qt windows). The first three layers contain no Qt code and are also driven by a console test program, which shows that the GUI is only one client of the same core.

2. System features

  • Register, edit and delete General, Emergency and Follow-Up patients; every field is validated.
  • Schedule, cancel and complete appointments; double bookings, impossible dates and invalid times are rejected.
  • Waiting queue: emergency patients are served first, everyone else first come, first served; “Call next patient”.
  • Search by ID, name or category with a choice of technique; sort by name, ID or age with a choice of algorithm.
  • Undo of the last administrative operation (delete patient, edit patient, cancel appointment) using a stack.
  • Four reports (most frequently attended, pending appointments, category distribution, daily summary), exportable to a text file.
  • Save and load to a text (CSV-style) file; a corrupt file is rejected and changes nothing.
  • Dashboard with live statistics, appointment reminders and a waiting-time alert (all timer-driven); keyboard shortcuts, tooltips and file dialogs.

3. Class hierarchy

PatientRecord is an abstract class holding the shared data (ID, name, age, contact) and three pure virtual functions: getCategory(), getPriority() and getSummary(). GeneralPatient, EmergencyPatient and FollowUpPatient derive from it and add their own data (complaint; severity and condition; previous diagnosis and last visit date). Appointable is an interface (pure virtual functions only) implemented by General and Follow-Up patients; emergency patients are walk-ins and are not appointable.

Composition: each appointable patient owns an AppointmentBook, which owns its Appointment objects (a patient has one or more appointments); ClinicDatabase owns every patient through a vector<PatientRecord*> and deletes them. Polymorphism: WaitingQueue::join(const PatientRecord&) picks a lane by calling the virtual getPriority(); the reports, tables and file writer also work through base-class pointers; in the GUI every tab is refreshed through the abstract ClinicPanel::refresh(), and every undo action through UndoAction::undo(). 5. Searching algorithms used

All searches are written by hand in SearchEngine and report how many comparisons they made. Linear search by patient ID works on any list, so it is used when the data is unsorted. Binary search by ID or exact name needs a sorted list; ClinicManager remembers how the list is ordered and any change (add, edit, delete, load) marks it “unsorted”, so binary search refuses to run on stale data. A recursive search finds every patient whose name contains a keyword. In “Automatic” mode an ID search tries the recent-patients cache first, then binary search if the list is sorted by ID, otherwise linear search.

6. Sorting algorithms used

Insertion sort and merge sort are implemented in Sorter (no library sort is used). Patients can be sorted by name, ID or age; the user chooses the algorithm and field in two combo boxes, and the number of comparisons is displayed afterwards. Sorting reorders only the list shown in the tables, never the database that owns the patients.

7. Recursive algorithm used

recursiveFind in SearchEngine calls itself with the next index. Base case 1: the index has reached the end of the list (return −1). Base case 2: the current patient's name contains the keyword (return the index). Recursive case: try the next patient. Merge sort is also recursive: it splits the list in half until one item remains, then merges the halves. The depth of the name search equals the list length, which is acceptable for a clinic's patient list.

8. GUI design

The main window (QMainWindow) has a menu bar (File, Edit, Help), six tabs — Dashboard, Patient Records, Appointments, Waiting Queue, Search & Sort, Reports — and a status bar. Every tab derives from the abstract ClinicPanel. A panel never owns clinic data: it sends requests to the single ClinicManager and emits dataChanged(), and MainWindow then refreshes all tabs, so panels do not depend on each other. Layouts: QVBoxLayout and QHBoxLayout arrange tables beside forms and resize with the window, QFormLayout aligns labels with fields, and a QStackedWidget shows only the extra fields that suit the chosen patient type. Events: button clicks, menu actions, table selection, combo-box changes, text changes (live search), the Enter key and three QTimers. Advanced features: rows coloured by category and appointment status, dynamic form fields, file dialogs (load, save, export), timers (dashboard refresh every 5 s, appointment reminders every 15 s, waiting-time alert every 1 s), validation dialogs, shortcuts (Ctrl+S, Ctrl+F, Ctrl+Q, Ctrl+N, Ctrl+O, Ctrl+Z) and tooltips.

9. Exception handling approach

A custom hierarchy derives from std::runtime_error: ClinicException is the base, with InvalidDataException (bad name, age, contact, date, time or search input), DuplicateIdException and FileException. Validator throws these; ClinicDatabase::addPatient checks everything before changing anything, so a failed operation leaves the data untouched. FileHandler reads a file into a temporary database and replaces the real one only if the whole file is valid; errors include the line number. The GUI catches ClinicException and shows what() in a dialog instead of crashing. Where memory must be released before an error continues upward, catch (...) deletes the object and rethrows; the timer handlers catch exceptions so one bad record cannot stop the program.

10. Algorithms chosen and reasons

ChoiceReason
Insertion sortBest for small or nearly sorted lists such as a clinic list with one new patient: 499 comparisons for 500 already-sorted patients.
Merge sortAlways about n log n, so it suits large or unpredictable lists: 2,216 comparisons for 500 reverse-sorted patients, against 124,750 for insertion sort.
Linear searchWorks on unsorted data with no preparation.
Binary searchHalves the search space each step; on the 5-patient test list it needed 2 comparisons against 4 for linear search. It requires sorted data, which the program checks.
Recursive searchExpresses “check this patient, then search the rest” directly and finds every partial name match.
Queue (two lanes)First in, first out is fair; the emergency lane lets urgent patients go first.
StackUndo must reverse the most recent operation first: last in, first out.

11. Challenges encountered

  1. VS Code compiled with gcc instead of g++, giving “undefined reference to std::cout” linker errors.
  2. Memory ownership of polymorphic pointers: leaks and dangling pointers were possible (cache, queue, undo, table list).
  3. Several structures had to stay consistent: deleting or loading patients while the cache, queue and undo stack still referred to them.
  4. Binary search returned wrong answers if the list was no longer sorted.
  5. Undo first restored only name, age and contact, not type-specific fields or appointments.
  6. A bad data file could leave the program half-loaded.
  7. Qt: a variable named slots clashed with a Qt macro, and signal/slot classes need the moc code generator.
  8. Time-based features (reminders) were hard to test because they depend on the clock.

12. How the challenges were resolved

  1. The build task was changed to g++ and later replaced by CMake; reading the first linker error showed which definition was missing.
  2. One-owner rule: ClinicDatabase owns patients, the queue stores IDs, the cache and table list are non-owning, a deleted patient belongs to its undo action; virtual destructors and unique_ptr for actions.
  3. ClinicManager performs each operation as one step (remove from cache and queue before deleting; reset cache, queue and undo history after loading).
  4. The list order is recorded and any change resets it to “unsorted”; binary search refuses to run otherwise.
  5. Undo stores a full PatientData snapshot and PatientFactory::apply restores it; a deleted patient is kept alive with its appointments; a cancelled appointment is reopened.
  6. Loading goes through a temporary database with line-numbered errors; the real data is replaced only after the whole file passes.
  7. The variable was renamed, and CMake’s AUTOMOC runs moc automatically.
  8. ReminderService takes the current time as a parameter and was tested with fixed times (a separate test program).
